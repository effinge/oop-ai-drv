Создай диаграмму состояний бизнес-проекта "Бизнес-центр" по его описанию ниже:
================================================================
1. КОНТЕКСТ И ЦЕЛЬ
================================================================

Система управления доступом бизнес-центра. Центральный объект с явным
жизненным циклом — пропуск (электронная запись, дающая право входа в БЦ).
Требуется диаграмма состояний (stateDiagram-v2), отражающая все допустимые
переходы статусов пропуска, их триггеры, акторов и условия.

Диаграмма — про статусы ОДНОГО пропуска. Пользователи, арендаторы,
уведомления, журнал — это внешние акторы и побочные эффекты (их следует
вынести в заметки/подписи переходов, а не в отдельные состояния).

Правила ролей и CRUD-операции в состояния не превращать: роли — это
ограничения (guard) на переходах.

================================================================
2. СОСТОЯНИЯ (РОВНО ПЯТЬ + НАЧАЛЬНОЕ И КОНЕЧНОЕ)
================================================================

Названия состояний на диаграмме — по-русски, в скобках можно указать код
из модели данных.

| Состояние      | Код       | Смысл                                                        | Видимость охране                    |
|----------------|-----------|--------------------------------------------------------------|-------------------------------------|
| Черновик       | draft     | Заявка создана, но срок действия ещё не начался.             | серый ⛔ НЕ АКТИВЕН                 |
|                |           | Для прохода недействителен.                                  |                                     |
| Активен        | active    | Пропуск действителен для прохода.                            | зелёный ✅ АКТИВЕН                  |
| Заблокирован   | blocked   | Принудительно недействителен, причина блокировки             | красный ⛔ ЗАБЛОКИРОВАН + причина   |
|                |           | обязательна. Обратим.                                        |                                     |
| Просрочен      | expired   | Срок действия истёк автоматически. Недействителен.           | ⛔ ПРОСРОЧЕН                        |
| Архив          | archive   | ТЕРМИНАЛЬНЫЙ статус: выведен из оборота, необратимо.         | ⛔ АРХИВ                            |

Дополнительно:
- Начальное псевдосостояние [*] — момент создания пропуска.
- Конечное псевдосостояние [*] — только из состояния «Архив».
- Отдельного состояния «Не найден» НЕТ — это результат поиска в интерфейсе
  охраны, а не статус пропуска.
- Статусов «деактивирован», «удалён», «истёк» не существует: в спецификации
  это запрещено; «деактивировать» = «заблокировать».

================================================================
3. ПЕРЕХОДЫ
================================================================

Формат: из → в, триггер, актор, условие (guard), побочные эффекты.

----------------------------------------------------------------
3.1. ВОЗНИКНОВЕНИЕ ПРОПУСКА
----------------------------------------------------------------

1) [*] → Черновик
   - Триггер: создание пропуска.
   - Актор: менеджер арендатора (только свой арендатор) или администратор БЦ
     (за любого арендатора).
   - Guard: valid_from > сегодня.
   - Эффекты: генерация уникального номера BC-XXXXXX; запись в журнал
     «создание».

2) [*] → Активен
   - Триггер: создание пропуска.
   - Актор: менеджер арендатора (свой) или администратор БЦ (любой, в т.ч.
     гостевой «walk-in» на текущий день).
   - Guard: valid_from <= сегодня. Прошедшая дата не допускается — система
     подставляет сегодняшнюю.
   - Эффекты: номер BC-XXXXXX; журнал «создание»; счётчик активных пропусков
     арендатора +1.

----------------------------------------------------------------
3.2. ШТАТНЫЕ ПЕРЕХОДЫ
----------------------------------------------------------------

3) Черновик → Активен
   - Триггер: наступление даты начала действия (valid_from). Способ —
     автоматически (ежедневная задача и/или проверка при чтении) либо
     вручную администратором.
   - Guard: valid_from <= сегодня <= valid_until.
   - Эффекты: журнал «активация».

4) Активен → Заблокирован
   - Триггер: команда «Заблокировать» с обязательной причиной из списка:
     потеря, кража, увольнение, по запросу арендатора, задолженность, иное
     (+свободный текст).
   - Актор: ТОЛЬКО администратор БЦ. Менеджер арендатора блокировать не
     может — он лишь создаёт запрос (см. раздел 5).
   - Guard: текущий статус «Активен».
   - Эффекты: block_reason, blocked_by, blocked_at; журнал «блокировка»;
     уведомление арендатору (email + in-app); новый статус виден охране
     не позднее 5 сек.

5) Активен → Просрочен
   - Триггер: автоматическая ночная задача (cron, ~00:05) и/или проверка при
     чтении.
   - Актор: система.
   - Guard: valid_until < сегодня.
   - Эффекты: журнал «истечение срока»; уведомление арендатору (напоминания
     за 3 дня и в день истечения — это отдельные уведомления, не переходы).

6) Активен → Архив
   - Триггер: команда «Архивировать» с подтверждением необратимости.
   - Актор: администратор БЦ (всегда) или менеджер арендатора (только свои
     пропуска).
   - Guard: нет (кроме необратимости).
   - Эффекты: журнал «архивирование»; пропуск скрывается из основного списка,
     остаётся в фильтре «архив».

7) Заблокирован → Активен
   - Триггер: команда «Разблокировать».
   - Актор: только администратор БЦ.
   - Guard: срок действия НЕ истёк (valid_until >= сегодня).
   - Эффекты: журнал «разблокировка»; охрана снова видит ✅ АКТИВЕН.

8) Заблокирован → Просрочен
   - Триггер: команда «Разблокировать».
   - Актор: только администратор БЦ.
   - Guard: срок действия УЖЕ истёк (valid_until < сегодня).
   - Эффекты: журнал «разблокировка» (с фиксацией перехода в просроченное
     состояние).

9) Просрочен → Активен
   - Триггер: продление срока — редактирование даты окончания на
     будущую/сегодняшнюю.
   - Актор: ТОЛЬКО администратор БЦ.
   - Guard: новая valid_until >= сегодня.
   - Эффекты: журнал «редактирование»; пропуск снова действителен для прохода.

10) Заблокирован → Архив
    - Триггер: «Архивировать».
    - Актор: администратор БЦ / менеджер арендатора (свой пропуск).
    - Комментарий: спецификация не запрещает архивировать заблокированный
      пропуск (ограничение только «неархивный статус»).

11) Черновик → Архив
    - Триггер: «Архивировать» (отказ от заявки, ошибочно созданный пропуск).
    - Актор: администратор БЦ / менеджер арендатора (свой).

12) Просрочен → Архив
    - Триггер: «Архивировать».
    - Актор: администратор БЦ / менеджер арендатора (свой).

----------------------------------------------------------------
3.3. МАССОВЫЙ ПЕРЕХОД
----------------------------------------------------------------

13) Любой неархивный статус (Черновик, Активен, Заблокирован, Просрочен)
    → Архив
    - Триггер: деактивация арендатора (tenant.is_active = false) при
      расторжении договора.
    - Актор: администратор БЦ.
    - Эффекты: ОДНОЙ операцией все пропуска арендатора переводятся в
      «Архив»; по каждому — запись журнала «архивирование» с основанием
      «деактивация арендатора»; создание новых пропусков от имени арендатора
      становится невозможным.
    - На диаграмме это удобно показать одним переходом из суперсостояния
      либо пунктирными стрелками из всех четырёх статусов с общей подписью.

----------------------------------------------------------------
3.4. ТЕРМИНАЛЬНОСТЬ
----------------------------------------------------------------

14) Архив → [*]
    - Переходов из «Архива» нет: нельзя разблокировать, продлить,
      отредактировать, повторно активировать. Только создать новый пропуск
      (новый номер, номера не переиспользуются).

================================================================
4. КЛЮЧЕВЫЕ ИНВАРИАНТЫ (ОБЯЗАТЕЛЬНО ОТРАЗИТЬ, НАПРИМЕР ЗАМЕТКАМИ)
================================================================

1. Блокировка приоритетнее срока. Если пропуск заблокирован и срок при этом
   истёк — он ОСТАЁТСЯ «Заблокирован», автоматического перехода в «Просрочен»
   нет. Поэтому стрелку «Активен → Просрочен» нельзя считать применимой к
   заблокированным.
2. «Архив» — единственный терминальный статус. Остальные обратимы (кроме
   необратимости самого архивирования).
3. Проверка охраной и просмотр карточки НЕ меняют статус — это
   самопереходы/наблюдения, а не переходы автомата. На диаграмме лучше
   показать заметкой: «Проверка (поиск по номеру/ФИО) фиксируется в журнале,
   статус не изменяется».
4. ФИО держателя можно менять только в «Черновике»; для администратора это
   правило тоже действует. Передача пропуска другому лицу — только через
   создание нового пропуска.
5. Редактирование: менеджер — только свои пропуска в статусах «Черновик» и
   «Активен»; администратор — любой неархивный, но не ФИО.
6. Охрана — read-only: не создаёт, не блокирует, не разблокирует, не
   архивирует.
7. Каждый переход пишется в журнал (append-only) с инициатором, временем,
   старым/новым значением и причиной (для блокировки).
8. Уведомления — best effort, не влияют на переход: блокировка, истечение
   срока, решение по запросу на блокировку.

================================================================
5. ВТОРАЯ (НЕОБЯЗАТЕЛЬНАЯ) ДИАГРАММА: «ЗАПРОС НА БЛОКИРОВКУ»
================================================================

Если нужно показать полный процесс, добавьте отдельную маленькую диаграмму
состояний сущности BlockRequest — она связана с состоянием «Активен»:

- [*] → Ожидает рассмотрения (pending): менеджер арендатора отправляет запрос
  на блокировку своего пропуска (причина из того же списка). Пропуск при этом
  ОСТАЁТСЯ «Активен» и охрана продолжает его пропускать. Журнал: «запрос на
  блокировку».
- Ожидает рассмотрения → Принят (approved): администратор БЦ подтверждает.
  Эффект: пропуск переходит «Активен → Заблокирован», причина подставляется
  из запроса; уведомление менеджеру.
- Ожидает рассмотрения → Отклонён (rejected): администратор отклоняет.
  Пропуск не меняется; уведомление менеджеру; журнал.
- Принят / Отклонён → [*]: терминальные состояния запроса.
- «Принят» и «Отклонён» — разные конечные состояния, обратных переходов нет;
  повторный запрос — новая сущность.

================================================================
6. ПОЖЕЛАНИЯ ПО ОФОРМЛЕНИЮ ДЛЯ MERMAID
================================================================

- Направление сверху вниз (direction TB) или слева направо: старт →
  Черновик/Активен → (Блокировка/Просрочка) → Архив.
- Подписи переходов в формате «действие [актор] / условие», например:
  «блокировка (админ БЦ, причина обязательна)».
- Автоматические (системные) переходы — пунктиром; ручные команды
  пользователей — сплошной линией.
- «Архив» визуально отделить (справа/внизу) и подписать «терминальный
  статус».
- Каждому состоянию — короткая заметка с русским названием статуса для охраны
  и кодом (draft, active, blocked, expired, archive).
- Добавьте легенду: ✅/⛔ и соответствие «статус → экран охраны».
- Не смешивайте на одной диаграмме жизненный цикл пропуска и жизненный цикл
  запроса на блокировку: это две сущности.

================================================================
7. НЕОДНОЗНАЧНОСТИ СПЕЦИФИКАЦИИ (ПЕРЕДАТЬ MERMAID AI КАК ДОПУЩЕНИЯ)
================================================================

1. Триггер перехода Черновик → Активен явно не назван: разумно показать
   автоматический переход по наступлению valid_from (ежедневная
   задача/проверка при чтении) + возможность ручной активации администратором.
2. Возможность блокировки просроченного пропуска не описана. Формально
   администратор может блокировать любой неархивный пропуск; если такой
   переход нужен — добавьте «Просрочен → Заблокирован» пунктиром с пометкой
   «допущение».
3. Судьба черновика с уже истёкшим сроком (дата начала и окончания в прошлом)
   не описана: возможен вариант «Черновик → Просрочен» пунктиром как
   допущение.
4. Очистка полей block_reason / blocked_by / blocked_at при разблокировке не
   оговорена — на диаграмме это не переход, а побочный эффект; достаточно
   упомянуть в заметке.
5. Уведомление при архивировании в требованиях не перечислено (FR-8.1),
   поэтому не рисуйте его обязательным эффектом перехода в «Архив».
