# Спецификация системы управления доступом в бизнес-центре

**Версия:** 1.0
**Дата:** 8 октября 2026 г.

---

## 1. Словарь терминов

| Термин | Определение |
|---|---|
| **Бизнес-центр (БЦ)** | Здание (здание с несколькими входами), в котором расположены арендованные помещения. Единица, для которой работает система. |
| **Арендатор** | Юридическое лицо, арендующее помещение в БЦ. Имеет учётную запись в системе и может заказывать пропуска для своих сотрудников и гостей. |
| **Администратор БЦ** | Сотрудник управляющей компании (или самой БЦ), управляющий системой: блокирует/разблокирует пропуска, управляет арендаторами. Высшая роль по правам. |
| **Охрана** | Сотрудник службы охраны, работающий на пункте пропуска. Имеет доступ к справочнику пропусков для проверки (read-only), но не может создавать, блокировать или разблокировать пропуска. |
| **Менеджер арендатора** | Пользователь от лица арендатора, уполномоченный заказывать и просматривать пропуска своего арендатора. |
| **Пропуск** | Электронная запись, дающая право человеку на вход в БЦ. Имеет уникальный идентификатор, тип, статус и срок действия. Может быть воплощён в физическую карту/брелок с номером или QR-кодом (вне рамок системы). |
| **Держатель пропуска** | Физическое лицо, на которое оформлен пропуск (сотрудник или гость арендатора). |
| **Сотрудник** | Держатель пропуска, работающий у арендатора на постоянной основе. Пропуск действует весь период действия. |
| **Гость** | Держатель пропуска, приглашённый арендатором на ограниченный срок (одно посещение или несколько в пределах окна). |
| **Тип пропуска** | Классификация пропуска: `сотрудник` или `гость`. Определяет срок действия и логику продления. |
| **Статус пропуска** | Состояние пропуска в данный момент: `черновик`, `активен`, `заблокирован`, `просрочен`, `архив`. См. раздел 4. |
| **Блокировка** | Действие, переводящее пропуск в статус `заблокирован`. После блокировки пропуск недействителен для прохода. Обратима (разблокировка). В версии 1.0 выполняется только администратором БЦ. |
| **Разблокировка** | Действие, возвращающее заблокированный пропуск в `активен` (если срок действия не истёк) либо в `просрочен` (если истёк). Доступна только администратору БЦ. |
| **Архивирование** | Необратимое выведение пропуска из оборота (статус `архив`). Не путать с блокировкой. |
| **Срок действия** | Период, в течение которого пропуск действителен (дата начала — дата окончания). По истечении пропуск автоматически переходит в статус `просрочен`. |
| **Зона доступа** | Часть БЦ (вход, этаж, паркинг и т.п.), в которую разрешён проход по пропуску. *В версии 1.0 не используется — все пропуска действуют на весь БЦ.* |
| **Пункт пропуска** | Место контроля (стойка охраны у входа), с которого выполняется проверка пропусков. |
| **Журнал событий** | Хронологическая запись действий в системе: создание, редактирование, активация, блокировка, разблокировка, архивирование, проверка, просмотр карточки — с указанием пользователя и времени. Регистрация проходов (вход/выход) в журнал не входит (вне scope 1.0). |
| **Сессия проверки** | Действие охраны: поиск пропуска и просмотр его текущего статуса. |
| **Запрос на блокировку** | Обращение менеджера арендатора к администратору БЦ с просьбой заблокировать пропуск (например, при потере). Сам менеджер пропуск не блокирует. |
| **Уведомление** | Сообщение, отправляемое арендатору (email или внутри системы) о событии, касающемся его пропусков. |
| **Архив** | Терминальный статус пропуска: пропуск выведен из оборота (уволенный сотрудник, расторгнутый договор). Из статуса `архив` переходов нет. |

## 2. Назначение и границы системы

### 2.1. Назначение
Система управления доступом (СУД) обеспечивает:
1. Регистрацию и учёт пропусков для сотрудников и гостей арендаторов БЦ.
2. Предоставление охране актуального справочника пропусков для проверки при входе.
3. Контроль срока действия пропусков.
4. Возможность блокировки пропуска администратором БЦ.
5. Аудит действий с пропусками.

### 2.2. Входит в scope (версия 1.0)
- Учётная запись и роли (администратор, менеджер арендатора, охрана).
- CRUD пропусков в рамках ролей.
- Назначение и автоматическое истечение срока действия.
- Блокировка / разблокировка пропуска администратором.
- Поиск и просмотр пропуска охраной.
- Журнал событий (аудит).
- Уведомления арендатору о ключевых событиях.

### 2.3. Вне scope (версия 1.0)
- Интеграция с турникетами, СКУД, физическим считывателями карт.
- Выпуск физических карт / печать QR-кодов.
- Зональный доступ (разные зоны для разных пропусков).
- Хранение персональных документов, сканов, фотографий.
- Онлайн-оплата, тарифы, биллинг.
- Мобильное приложение.
- Мультиздание / мультигород.
- Интеграция с 1С / HR-системами арендаторов.

## 3. Роли и права доступа

| Действие | Администратор БЦ | Менеджер арендатора | Охрана |
|---|---|---|---|
| Просмотр списка **всех** пропусков | ✅ | ❌ (только свои) | ✅ |
| Просмотр **чужого** пропуска | ✅ | ❌ | ✅ |
| Создание пропуска | ✅ (за любого арендатора) | ✅ (только свой арендатор) | ❌ |
| Редактирование пропуска (срок, данные) | ✅ (кроме ФИО после черновика) | ✅ (только свой, до активации) | ❌ |
| Блокировка пропуска | ✅ | ❌ (может только запросить) | ❌ |
| Разблокировка пропуска | ✅ | ❌ | ❌ |
| Запрос на блокировку (инициирование) | ❌ (блокирует сразу) | ✅ (только свой) | ❌ |
| Архивирование пропуска | ✅ | ✅ (только свой) | ❌ |
| Управление арендаторами | ✅ | ❌ | ❌ |
| Просмотр журнала событий | ✅ | Только по своим пропускам | ❌ |
| Управление пользователями и ролями | ✅ | ❌ | ❌ |

**Правило:** у охраны доступ read-only. Охрана не может ни создавать, ни блокировать, ни разблокировать пропуска — только искать и просматривать.
**Термин «деактивировать пропуск» в спецификации не используется** — во избежание двойного толкования применяются однозначные термины «блокировка» и «архивирование». Ранее встречавшееся «деактивировать» трактуется как «заблокировать» (обратимо).

## 4. Жизненный цикл пропуска

### 4.1. Статусы

```
черновик ──► активен ──► заблокирован ──► активен (разблокировка)
    │            │
    │            └──► просрочен (по дате окончания)
    │                     │
    └──► архив             └──► архив (по решению администратора)
```

| Статус | Описание | Кто переводит |
|---|---|---|
| `черновик` | Заявка создана, но ещё не активирована (не действует для прохода). | Система при создании, если указана будущая дата начала |
| `активен` | Пропуск действителен для прохода. | Система (при создании с сегодняшней датой) / администратор |
| `заблокирован` | Пропуск недействителен, охрана получает отказ при проверке. | Администратор БЦ |
| `просрочен` | Срок действия истёк автоматически. Недействителен. | Система (по расписанию) |
| `архив` | Пропуск выведен из оборота (уволенный сотрудник, расторгнутый договор). Необратимо. | Администратор / менеджер арендатора |
**Правила переходов:**
- `заблокирован → активен` — только администратором, если срок действия не истёк.
- `просрочен → активен` — только продлением срока действия (редактирование даты окончания администратором).
- `архив` — терминальный статус, переходов из него нет.
- Блокировка имеет приоритет над сроком: если пропуск заблокирован и срок истёк — он остаётся `заблокированным` до решения администратора (не `просроченным`).

### 4.2. Переход «просрочен»
- Ночная задача (cron) раз в сутки (и/или проверка при чтении) переводит в `просрочен` все пропуска с `дата_окончания < текущая_дата`.
- При переводе отправляется уведомление арендатору.

## 5. Функциональные требования

### FR-1. Управление учётными записями
- **FR-1.1** Администратор БЦ создаёт, редактирует и деактивирует учётные записи арендаторов и их менеджеров.
- **FR-1.2** Администратор назначает роли: `admin`, `tenant_manager`, `security`.
- **FR-1.3** Аутентификация по логину + пароль (первая версия). Смена пароля — самостоятельно пользователем.
- **FR-1.4** Каждый арендатор имеет уникальное наименование и реквизиты (ИНН, контактное лицо, телефон).

### FR-10. Ограничения и лимиты
- **FR-10.1** Верхняя граница срока действия пропуска сотрудника — по умолчанию не более 1 года; настраивается администратором.
- **FR-10.2** Лимит активных пропусков на арендатора не задан по умолчанию; настраивается администратором (по умолчанию — без ограничения).
- **FR-10.3** При создании второго активного пропуска на одно и то же ФИО в рамках одного арендатора система показывает предупреждение о возможном дубле, но создание не блокирует.

### FR-2. Управление пропусками (создание)
- **FR-2.1** Менеджер арендатора создаёт пропуск, указывая:
  - тип (`сотрудник` / `гость`);
  - ФИО держателя;
  - контактный телефон (опционально);
  - дату начала и дату окончания действия;
  - для гостя — дату(ы) визита (укороченный срок).
- **FR-2.2** Система автоматически генерирует уникальный номер пропуска (формат: `BC-XXXXXX`, латиница + цифры, уникален в системе).
- **FR-2.3** Пропуск создаётся сразу в статусе `активен`, если дата начала ≤ сегодня; иначе — `черновик`. Дата начала **в прошлом не допускается**: при попытке указать прошедшую дату система подставляет текущую дату (оформление «задним числом» запрещено).
- **FR-2.4** Для типа `гость` максимальный срок действия по умолчанию — 7 дней (настраивается администратором). В отличие от сотрудника, пропуск гостя ограничен окном визита и не действует вне его.
- **FR-2.5** Администратор может создать пропуск от имени любого арендатора (в том числе гостевой «walk-in» на месте, если гость пришёл без заявки). Менеджер арендатора создаёт пропуска только своего арендатора.
- **FR-2.6** Охрана не может создавать пропуска.

### FR-3. Просмотр и поиск пропусков
- **FR-3.1** Список пропусков отфильтрован по роли: арендатор видит только свои, охрана и администратор — все.
- **FR-3.2** Поиск по номеру пропуска, ФИО держателя, названию арендатора, статусу, дате окончания.
- **FR-3.3** Карточка пропуска содержит: номер, тип, ФИО, арендатора, статус, период действия, дату последнего изменения, кто изменил.
- **FR-3.4** Список отсортирован по дате окончания (ближайшие первыми) — для охраны и администратора.

### FR-4. Редактирование пропуска
- **FR-4.1** Менеджер арендатора может редактировать пропуск только в статусах `черновик` и `активен` и только свой.
- **FR-4.2** Изменение ФИО держателя допускается только в статусе `черновик` (человек не начинал ходить).
- **FR-4.3** Продление срока действия выполняется только администратором (изменение даты окончания).
- **FR-4.4** Администратор может редактировать любой пропуск в любом неархивном статусе — **кроме ФИО держателя** (правило FR-4.2 действует и для администратора). Передача пропуска другому человеку оформляется созданием нового пропуска, а не редактированием.

### FR-5. Блокировка и разблокировка
- **FR-5.1** Заблокировать пропуск может только администратор БЦ.
- **FR-5.2** При блокировке указывается причина (список: `потеря`, `кража`, `увольнение`, `по запросу арендатора`, `задолженность`, `иное` — свободный текст при `иное`).
- **FR-5.3** Блокировка мгновенно отражается в статусе, видимом охране (без задержек кэширования > 5 сек).
- **FR-5.4** Разблокировка возвращает пропуск в статус `активен`, если срок действия не истёк; иначе — в `просрочен`.
- **FR-5.5** Каждое действие блокировки/разблокировки фиксируется в журнале событий.
- **FR-5.6** Менеджер арендатора при подозрении на потерю пропуска может отправить администратору **запрос на блокировку** (отдельная сущность `запрос`), но не блокирует сам. Администратор рассматривает запрос (принимает/отклоняет); при принятии пропуск блокируется.
- **FR-5.7** Охрана не может блокировать, разблокировать и создавать пропуска (read-only).
- **FR-5.8** Блокировка останавливает новые проходы, но не инициирует выдворение человека, уже находящегося в здании.

### FR-6. Проверка пропуска охраной
- **FR-6.1** Интерфейс охраны — экран с полем поиска (номер пропуска / ФИО) в фокусе.
- **FR-6.2** Поиск по номеру — точный, по ФИО — частичный (без учёта регистра).
- **FR-6.3** Результат проверки отображается явно:
  - ✅ `АКТИВЕН` (зелёный) — ФИО, фото не требуется, арендатор, срок;
  - ⛔ `ЗАБЛОКИРОВАН` (красный) — с указанием причины блокировки;
  - ⛔ `НЕ АКТИВЕН` (серый) — черновик (пропуск создан, но дата начала не наступила);
  - ⛔ `ПРОСРОЧЕН` / `АРХИВ` / `НЕ НАЙДЕН`.
- **FR-6.4** Результат проверки фиксируется в журнале событий (событие `проверка`) с привязкой к учётной записи охраны (инициатор = пользователь-охранник). Персональные данные проверяемого в запись не добавляются.
- **FR-6.5** Интерфейс охраны доступен без дополнительной навигации (максимум 2 действия от входа до результата).

### FR-7. Архивирование
- **FR-7.1** Архивирование доступно администратору (всегда) и менеджеру арендатора (только свои пропуска).
- **FR-7.2** Архивирование необратимо; архивные пропуска скрыты из основного списка, доступны по фильтру.
- **FR-7.3** При расторжении договора аренды администратор деактивирует арендатора → все его пропуска массово переводятся в `архив` одной операцией.

### FR-8. Уведомления
- **FR-8.1** Арендатор получает уведомление (email, если указан) при:
  - истечении срока действия пропуска (за 3 дня и в день истечения);
  - блокировке пропуска;
  - отклонении/принятии запроса на блокировку.
- **FR-8.2** Уведомления дублируются внутренними сообщениями в интерфейсе арендатора (канал `in_app`). Email — основной канал; внутреннее сообщение — дублирующий.
- **FR-8.3** Опция «уведомления отключены» — настройка на уровне арендатора.
- **FR-8.4** Уведомление — best effort: недоставка email не отменяет и не откатывает действие над пропуском.

### FR-9. Журнал событий (аудит)
- **FR-9.1** Система фиксирует: `создание`, `редактирование`, `активация`, `блокировка`, `разблокировка`, `архивирование`, `проверка`, `просмотр карточки`.
- **FR-9.2** Запись журнала: время (UTC+3), тип события, объект (пропуск), инициатор (пользователь), старое и новое значение (для изменений), причина (для блокировки).
- **FR-9.3** Журнал доступен администратору полностью; менеджеру арендатора — только по своим пропускам; охране — нет.
- **FR-9.4** Записи журнала неизменяемы и неудаляемы (append-only). Хранение — 3 года.

## 6. Модель данных (сущности и основные атрибуты)

### User (Пользователь)
- `id`, `email` (логин), `password_hash`, `role` ∈ {`admin`, `tenant_manager`, `security`}, `full_name`, `tenant_id` (nullable — для `tenant_manager`), `is_active`, `created_at`

### Tenant (Арендатор)
- `id`, `name`, `inn`, `contact_person`, `contact_phone`, `contact_email`, `lease_end_date`, `is_active`, `notifications_enabled`, `max_active_passes` (nullable — лимит активных пропусков)

### Pass (Пропуск)
- `id`, `number` (уникальный, `BC-XXXXXX`; генерируется системой, не переиспользуется), `type` ∈ {`employee`, `guest`}, `holder_name`, `holder_phone`, `tenant_id`, `status` ∈ {`draft`, `active`, `blocked`, `expired`, `archive`}, `valid_from`, `valid_until`, `block_reason` (nullable), `blocked_by` (nullable), `blocked_at` (nullable), `created_by`, `created_at`, `updated_at`

### BlockRequest (Запрос на блокировку)
- `id`, `pass_id`, `requested_by` (user), `status` ∈ {`pending`, `approved`, `rejected`}, `comment`, `processed_by`, `processed_at`, `created_at`, `reason` (причина, из списка FR-5.2)

### AuditLog (Журнал событий)
- `id`, `event_type`, `pass_id` (nullable), `tenant_id` (nullable), `actor_id`, `old_value` (JSON, nullable), `new_value` (JSON, nullable), `reason` (nullable), `created_at`

### Notification (Уведомление)
- `id`, `user_id`, `pass_id`, `channel` ∈ {`email`, `in_app`}, `template`, `status` ∈ {`queued`, `sent`, `failed`}, `created_at`, `sent_at`

## 8. Основные пользовательские сценарии

**US-1. Менеджер арендатора заказывает пропуск сотруднику**
1. Входит в систему → «Мои пропуска» → «Создать».
2. Выбирает тип «Сотрудник», вводит ФИО, телефон, даты действия.
3. Система генерирует номер, статус — `активен`.
4. Менеджер распечатывает/передаёт номер держателю.

**US-2. Менеджер заказывает пропуск гостю на конкретный день**
1. «Создать» → тип «Гость», ФИО, дата(ы) визита.
2. Срок автоматически ограничен окном визита (и не более 7 дней, FR-2.4).
3. Пропуск `активен` в пределах окна визита; вне окна — недействителен, после — `просрочен`.

**US-7. Гость без предварительной заявки (walk-in)**
1. Гость пришёл без заявки; охрана направляет его к администратору БЦ.
2. Администратор создаёт гостевой пропуск на месте (FR-2.5) на текущий день.
3. Пропуск `активен` на дату визита, охрана проверяет и пропускает.

**US-3. Охрана проверяет пропуск**
1. Открывает интерфейс охраны → поле поиска уже в фокусе.
2. Сканирует/вводит номер → результат: ✅ `АКТИВЕН` (+ ФИО, арендатор, срок) или ⛔ отказ с причиной.
3. Событие попадает в журнал.

**US-4. Администратор блокирует пропуск**
1. Находит пропуск → «Заблокировать» → выбирает причину → подтверждает.
2. Статус → `заблокирован`; охрана при следующей проверке видит отказ.
3. Арендатору уходит уведомление; действие — в журнале.

**US-5. Арендатор сообщает о потере пропуска**
1. Менеджер находит пропуск → «Запросить блокировку» → причина «потеря».
2. Администратор видит запрос в очереди → подтверждает → пропуск блокируется.
3. Менеджер создаёт новый пропуск взамен.

**US-6. Пропуск просрочен**
1. Ночная задача находит пропуск с истёкшим сроком → статус `просрочен`.
2. Охрана при проверке видит ⛔ `ПРОСРОЧЕН`.
3. Арендатор получает уведомление. Администратор может продлить срок → статус возвращается в `активен`.

## 9. Открытые вопросы (предположения для версии 1.0)

1. **Физические карты** — система не управляет их печатью; номер генерируется системой (`BC-XXXXXX`) и связывается с физическим носителем вручную вне системы. Номера не переиспользуются.
2. **Зоны доступа** — все пропуска действуют на весь БЦ; зональность не реализована (в модели данных зоны не заложены).
3. **Фото держателя** — не хранятся; охрана сверяет ФИО по паспорту по своему усмотрению.
4. **Массовое закрытие по арендатору** — при деактивации арендатора все его пропуска переводятся в `архив` (это архивирование, а не блокировка).
5. **Интеграция с турникетами** — отложена до версии 1.1.
6. **Регистрация проходов (вход/выход)** — не реализуется в 1.0; журнал фиксирует только действия над пропусками и проверки.
7. **Walk-in гости** — гость без предварительной заявки оформляется администратором БЦ (FR-2.5); охрана пропуска не создаёт.
8. **Забытый/утерянный/повреждённый пропуск** — альтернативная идентификация в 1.0 не реализована; вопрос направляется администратору БЦ.
9. **Чёрный список лиц** — понятие вводится в версии 1.1; в 1.0 контроль только через статус пропуска.
10. **Офлайн-режим охраны** — система предполагает постоянный онлайн-доступ; офлайн-кэш пропусков отложен.
